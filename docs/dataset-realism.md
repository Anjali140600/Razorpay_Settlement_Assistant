# Dataset realism & honest evaluation

Razorpay Settlement Assistant uses **two layers** of synthetic data so we can show both success and failure without cherry-picking.

## Layer 1 — Merchant mess simulator (`data/synthetic/demo/`)

Generated by `data/synthetic/generator.py` to mimic real Indian merchant settlement exports:

| Profile | What it simulates |
|---------|-------------------|
| `setl_merchant_d2c_*` (18×) | Everyday D2C — mixed UPI/card, occasional partial refunds |
| `setl_messy_flash_sale` | 16 micro-payments ₹49–₹299 (volume spike) |
| `setl_messy_saas` | High-ticket SaaS + partial refund |
| `setl_messy_marketplace` | Payments + linked transfers (marketplace payouts) |
| `setl_messy_refund_day` | Refund-heavy day — multiple partial refunds |
| `setl_messy_chargebacks` | Adjustment credits (chargeback reversals, fee reversals) |
| `setl_messy_zero_fee_upi` | Zero-MDR UPI promo (fee=0, tax=0) |
| `setl_messy_rounding_ok` | GST within ±1 paise — **passes** (real rounding edge) |
| `setl_messy_b2b` | High-ticket netbanking |
| `setl_messy_combo` | Everything in one settlement |

**API realism:** ~35% of lines use Unix timestamps (like live Razorpay recon API).

### Intentional failures (honest exception list)

| Settlement | Failure type | What broke |
|------------|--------------|------------|
| `setl_tax_mismatch` | Tax | Wrong GST on fee line |
| `setl_batch_mismatch` | Batch | Header ≠ recon net |
| `setl_fee_semantic_error` | Batch | credit ≠ amount − fee |
| `setl_refund_wrong_amount` | Tax | Refund debit ≠ amount |
| `setl_transfer_tax_wrong` | Tax | Transfer GST wrong |
| `setl_orphan_header_drift` | Batch | Header drift vs recon |

Labels are computed by `src/eval/independent_verifier.py` — **not** inline generator truth.

### Query-triage scenarios (auto-resolve vs support escalation)

Each is the same `SETTLEMENT_TOTAL_MISMATCH` shape as `setl_batch_mismatch` above; what
differs is the adjustment evidence elsewhere in the same recon feed, which is what
`src/agent/triage.py` inspects. See `tests/test_triage.py::test_ui_demo_dataset_covers_every_triage_scenario`
for the pinned verdict on each.

| Settlement | Triage verdict | What it demonstrates |
|------------|-----------------|----------------------|
| `setl_short_compensated` | `ALREADY_COMPENSATED` | A later adjustment (`setl_short_compensated_fix`) already binds the shortfall — nothing to file |
| `setl_ambiguous_shortfall` | `NEEDS_SUPPORT` (ambiguous) | Two adjustments both cleanly match the same shortfall — a person must pick the right one |
| `setl_unreconciled_shortfall` | `NEEDS_SUPPORT` (unreconciled) | An adjustment names this settlement but is one paise short — doesn't cleanly reconcile |
| `setl_over_settled` | `NEEDS_SUPPORT` (over-settlement) | Lines net *more* than the header — Razorpay's recovery, never a merchant claim |
| `setl_no_recon_lines` | `NEEDS_SUPPORT` (no clean delta) | A header with zero recon lines — no evidence to compute a compensable amount from |

## Layer 2 — Independent holdout (`data/fixtures/holdout/`)

**Hand-crafted JSON, NOT generated by the simulator.**

- 8 settlements, 17 recon lines
- Labels in `data/eval_holdout_labels.json` authored separately
- 5 verified + 3 needs attention
- Includes: D2C mix, marketplace transfer, zero-fee UPI, rounding tolerance, refund storm, tax fail, batch fail, semantic fail

Reported as **holdout_integrity_rate** and **holdout_labeled_accuracy** in metrics — separate from demo batch.

## What we claim (and what we don't)

| Claim | Valid? |
|-------|--------|
| Full batch throughput on 120+ lines | Yes |
| Integrity rate on **full** demo batch (not one match) | Yes — ~85% verified, ~15% exceptions |
| Honest exception export with payment IDs | Yes — 6 failure types |
| Holdout generalization | Partial — 8 independent fixtures |
| Production merchant accuracy | **No** — synthetic only; real redacted Razorpay recon is next step |
| Bank receipt proof | **No** — out of scope |

---

## Hackathon bar mapping

> Throughput + measured accuracy + honest exception list. One cherry-picked match proves nothing.

- **Throughput:** all recon lines processed; lines/sec in auditor expander  
- **Measured accuracy:** integrity rate on full batch + separate holdout rate  
- **Honest exceptions:** every failure exported with settlement_id, control type, bad line id  
- **Not cherry-picked:** 6 failures across tax, batch, refund, transfer, semantic errors
