# Razorpay field contract

Source of truth for synthetic data and deterministic controls. Derived from the [Razorpay combined recon API](https://razorpay.com/docs/api/settlements/fetch-recon/) and golden fixture `data/fixtures/recon_golden.json` (official doc sample — not generated by our synthetic pipeline).

## Scope

| Field / rule | INR domestic | Notes |
|--------------|--------------|-------|
| Amounts | Paise (integer) | All monetary fields in subunits |
| `fee` | GST-**inclusive** total MDR | Merchant sees one fee deduction |
| `tax` | GST on fee | `tax ≈ round(fee × 18/118)` |
| Tolerance | ±1 paise | Rounding on tax line |
| `credit` (payment) | `amount − fee` | Fee already includes GST |
| `debit` (payment) | `0` | |
| `debit` (refund) | `amount` | Reverses merchant credit |
| `credit` (refund) | `0` | |
| `debit` (transfer) | `amount + fee` | Per API transfer example |
| `credit` (transfer) | `0` | |
| Batch integrity | `Σ(credit − debit)` = settlement header `amount` | All line types |

## Formulas (implemented in `src/domain/razorpay_contract.py`)

```python
expected_tax = round(fee * 18 / 118)   # ±1 paise
payment.credit = amount - fee
transfer.debit = amount + fee
batch_net = sum(credit - debit for each line)
```

## Golden fixture validation

From Razorpay docs transfer line: `fee=296`, `tax=46` → `round(296 × 18/118) = 45` (within ±1 of published 46).

Payment line in same fixture: `fee=2900`, `tax=0` (USD — no Indian GST).

## Demo exceptions (synthetic only)

| Settlement ID | Injected defect | Expected label |
|---------------|-----------------|----------------|
| `setl_tax_mismatch` | One payment line with wrong `tax` | Needs attention — tax fail |
| `setl_batch_mismatch` | Header `amount` ≠ recon net | Needs attention — batch fail |

All other demo settlements follow this contract exactly.
